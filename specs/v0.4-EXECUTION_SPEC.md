# Pi Data Agent v0.4 执行 Spec｜网页端可视化(消息流+图表)

## 背景

pi-agent-dashboard 客户端实测未能连接现有 Pi Data Agent 会话——命令行正常启动，但没有拉起网页端，大概率是其内部的版本/包名检测逻辑与当前 SDK 组合没对上，静默降级成普通命令行模式。

调研确认：该项目依赖的 `@earendil-works/pi-coding-agent`，和我们使用的 SDK 其实是**同一个项目改名前后的版本**（`@mariozechner/*` 系列已全部废弃并映射到 `@earendil-works/*`），协议本身没有根本性差异。因此，没有必要照此前策划文档设想的"三层架构 + 协议转换"从零重建。

v0.4 改走更轻的路线：**不做常驻服务、不做协议桥接**，复用 v0.3 已有的报告生成能力，新增独立的 `generate_session_report` 工具，生成"任务级 HTML 报告"，每次生成后自动用系统默认浏览器打开。

## v0.4 定位

网页端可视化 · 第一步：消息流 + 图表内联

## 设计原则

1. **不修改 v0.3 已有工具** — `generate_report`（数据报告）保持不变，新增 `generate_session_report`（会话报告）作为独立工具
2. **不新建持久化层** — 复用 Pi SDK 内置的 `SessionManager`，它已以 JSONL 格式持久化完整对话树
3. **触发规则走 system prompt** — 不写入 `agent.md`（该文件在 v0.3 中被 `PersistenceManager` 用于存储口径记忆的 JSON），而是在 `before_agent_start` 的 system prompt 注入中追加行为规则

## 任务拆解（按执行顺序）

### Task 1｜会话消息读取与整理

- **文件**：`src/report/session-transcript.ts`（新建）
- **做什么**：
    - Pi SDK 的 `SessionManager` 已以 JSONL 格式持久化完整的 Session 树，每个 `SessionMessageEntry` 包含 `message: AgentMessage`（角色、内容、工具调用）、`timestamp`、`id`/`parentId`（树结构）。
    - 通过 `ctx.sessionManager.getBranch()` 获取当前分支的所有 entries。
    - 写一个 `getSessionTranscript(sessionManager)` 函数，遍历 entries，提取：
        - `role`：消息角色（user / assistant / tool_result）
        - `content`：消息文本内容
        - `timestamp`：时间戳
        - `toolCalls?`：工具调用信息（工具名、参数摘要、结果摘要），从 `AgentMessage` 的 tool_use / tool_result 内容块中提取
    - 过滤掉非消息类型 entries（如 `thinking_level_change`、`model_change`、`compaction`、`branch_summary`），只保留 `type: "message"` 的 entries。
- **不要做**：不新建 hook、不新增持久化逻辑、不重新设计持久化层。
- **验收**：写一个单元测试，mock 一个 SessionManager（返回预设的 entries 数组），调用 `getSessionTranscript` 后返回的 transcript 数组长度和字段完整性符合预期。

### Task 2｜HTML 报告模板与渲染引擎

- **文件**：`src/report/html-template.ts`（新建，纯字符串模板）、`src/report/render-report.ts`（新建，组装数据 → 调模板 → 输出字符串）
- **做什么**：
    - 模板包含：页头（任务标题、生成时间）、消息流区块（占位符 `MESSAGES`）、图表区块（占位符 `CHARTS`）
    - 消息流按气泡样式渲染，工具调用节点用简化摘要卡片（不展示原始 SQL，v0.4 阶段先不做语法高亮，留给 v0.5）
    - 工具调用卡片内容：工具名、参数摘要（截断到 200 字符，`query_data` 的 SQL 参数必须原样展示以满足可追溯性要求，见 v0.3 §2.2）、结果摘要（截断到 500 字符）、是否出错
    - 不引入 React / Vue 等前端框架，纯字符串拼接 + 内联 `<style>`
    - 暗色主题，与 pi-data-agent 的 TUI 风格保持一致
- **验收**：给定一份 mock transcript 数据，跑 `render-report.ts` 生成的 HTML 用浏览器打开，人工确认排版正常，无缺失字段。

### Task 3｜图表 base64 内联

- **文件**：`src/report/inline-assets.ts`（新建）
- **做什么**：
    - 扫描本次 session 中 `visualize` / `show_image` 产出的图表文件路径（从 transcript 的 toolCalls 中提取）
    - 逐个读取并转 base64，替换进 `<img src="data:image/png;base64,...">`
    - 设定单图大小阈值（建议 2MB），超过阈值时自动降采样或提示"图表过大，已跳过内联，路径见下"，避免报告文件体积失控
    - 设定报告总大小上限（建议 20MB），超过后停止内联剩余图表，统一列出路径
- **验收**：把生成的报告文件移动到另一个目录/发给另一台机器打开，图表依然正常显示（验证真正离线自包含）。

### Task 4｜新增 generate_session_report 工具

- **文件**：`src/tools/generate-session-report.ts`（新建）
- **做什么**：
    - **独立工具**，不修改 v0.3 的 `generate_report`（数据报告）
    - 工具名：`generate_session_report`
    - 参数 schema（TypeBox）：
        ```typescript
        Type.Object({
          title: Type.Optional(Type.String({ description: "报告标题（默认: 分析会话报告）" })),
          output_path: Type.Optional(Type.String({ description: "报告输出路径（默认: reports/session-<timestamp>.html）" })),
        })
        ```
    - 执行流程：
        1. 从 `ctx.sessionManager.getBranch()` 读取当前会话 entries
        2. 调用 Task 1 的 `getSessionTranscript()` 整理为 transcript
        3. 调用 Task 3 的图表内联逻辑处理图表路径
        4. 调用 Task 2 的 `renderReport()` 生成 HTML 字符串
        5. 写入本地文件（默认路径 `reports/session-<timestamp>.html`），`output_path` 必须经过 `security.checkPath()` 白名单验证
        6. 调用 Task 5 的 `openBrowser()` 自动打开
    - 返回值包含 `reportPath`、`messageCount`、`chartCount`、`fileSizeBytes`
- **不要做**：不加 `mode` 参数、不修改 `generate_report` 的 schema 或逻辑
- **验收**：手动调用一次该工具，检查文件是否生成在预期路径，内容是否完整。

### Task 5｜自动打开浏览器

- **文件**：`src/utils/open-browser.ts`（新建）
- **做什么**：
    - 用 `child_process.exec`，按 `process.platform` 分支：`darwin → open`，`win32 → start`，`linux → xdg-open`
    - 失败时（比如无图形环境的服务器/容器）捕获异常，降级为在终端打印报告的绝对路径，不让工具报错中断
- **验收**：本地跑一次，确认浏览器被拉起并打开正确文件；再模拟一次异常场景（比如传入不存在的路径），确认走的是降级分支而不是抛错。

### Task 6｜触发时机集成

- **文件**：`src/index.ts`（修改 `before_agent_start` 的 system prompt 注入）
- **做什么**：
    - 在 `before_agent_start` hook 的 system prompt 拼接中，追加一段行为规则（与现有的数据上下文、口径记忆等注入同级）：
        ```
        ### Session Report Rules
        - After completing a full analysis task (e.g., user asked a data question and you provided a complete answer with SQL + results + charts), proactively call generate_session_report to generate a visual session report.
        - When the user explicitly says "生成报告" / "给我看看结果" / "整理分析结果" / "generate report", call generate_session_report.
        - Do NOT call generate_session_report after every single tool call — only after a complete analysis cycle (≥ 2 tool calls have been made AND the user's question has been answered).
        - For data-specific reports (focused on a single query's results), use generate_report instead.
        ```
    - **不写入 `agent.md`**：该文件在 v0.3 中被 `PersistenceManager` 用于存储口径记忆的 JSON 格式数据，写入行为规则会破坏现有口径读写逻辑。
- **验收**：真实对话里说一句"帮我整理一下这次的分析结果"，观察是否正确触发 `generate_session_report` 且只触发一次。

### Task 7｜Should Have（时间允许再做，不阻塞验收）

- 锚点导航目录（`render-report.ts` 里按消息序号生成 `<a name>`）
- 深浅色主题切换（纯 CSS `prefers-color-scheme` 或页面内一个按钮切 class）
- 报告归档到 `reports/` 目录并按时间戳命名（Task 4 已经隐含，这里补充：旧报告不自动删除，允许用户回溯）

### Task 8｜测试与回归

- **文件**：`acceptance-v4.sh`（新建，参考 `acceptance-v3.sh` 结构）
- **测试场景（至少 3 个真实分析任务）**：
    1. 加载 CSV → 查询 → 生成图表 → 触发报告 → 断言报告文件存在、含消息流、含内联图表、浏览器被调用
    2. 连接 SQLite 数据库 → 多轮查询 → 触发报告 → 断言消息数量与实际轮次一致
    3. 用户中途打断/追问的场景 → 触发报告 → 断言消息流顺序正确不错乱
- **回归**：跑一次 v0.1/v0.2/v0.3 现有回归测试（`run-all-v2.ts` / `business-scenarios.test.ts`），确认新增代码没有破坏已有工具。

## 依赖关系

```
Task 1（消息读取）──┐
Task 2（模板引擎）──┼──> Task 4（generate_session_report）──> Task 6（触发集成）──> Task 8（测试）
Task 3（图表内联）──┘                    │
                                    Task 5（自动打开浏览器）
```

Task 1/2/3 可以并行开发，Task 4 依赖三者完成后再集成，Task 5 独立开发可随时并入。

## Deferred to v0.5

- SQL 卡片（展示实际执行的 SQL 语句，带语法高亮）
- 数据字典面板（展示当前字段确认状态：ai-guessed / user-confirmed / user-corrected / uncertain）
- 更完整的多 Session 浏览 / 切换能力

## 验收标准

- Task 8 的 3 个场景 + 回归测试全部通过
- 报告文件在断网、无常驻服务、被移动到其他目录/机器的情况下依然可以独立打开查看
- 单份报告生成到浏览器打开的耗时 < 3 秒（不含图表渲染本身耗时）
- 图表 base64 内联后单份报告文件大小有明确上限控制（超限走降级分支，不无限增长）
- v0.3 的 `generate_report` 工具行为无变化（向后兼容验证）

## 风险与注意事项

- 跨平台浏览器打开命令在部分 Linux 无图形环境下会失败，必须有降级分支（Task 5 已覆盖）
- 大量图表场景下报告体积可能过大，需要 Task 3 的阈值控制
- 是否需要延续 v0.3 的 PII 脱敏逻辑到消息流展示中（比如用户输入里包含的敏感路径/字段名）——建议直接复用现有 `pii-guard.ts`，不新写一套
- `SessionManager.getBranch()` 返回的 entries 可能包含 compaction 后的摘要条目，需要在 Task 1 中正确过滤
- AgentMessage 的 content 可能是 `TextContent`、`ImageContent`、`ToolUseContent`、`ToolResultContent` 的混合数组，Task 1/2 需要处理所有类型
