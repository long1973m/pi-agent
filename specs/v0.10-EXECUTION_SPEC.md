## 2. K-0：写令牌持久化 + 前端自愈（P0）

### 2.1 根因

令牌每次启动随机生成（lifecycle.ts:43），旧浏览器标签页持有上一会话的令牌，服务端重启后全部写请求报 `INVALID_WRITE_TOKEN`（"写令牌无效或缺失"）；前端无自愈逻辑，直接把错误甩给用户。而该令牌的实际安全作用仅为本地 CSRF 防护（`/api/config` 本来就会把令牌下发给任何本地页面），为此牺牲"重启后标签页可用"得不偿失。

### 2.2 修复方案

- 令牌持久化到 `.pi-data-agent/dashboard-token`（文件权限 0600）：启动时存在则复用，不存在（或格式非法）才生成新令牌并写入
- 前端 `api.fetch` 包装器：写请求收到 `INVALID_WRITE_TOKEN` 时，自动重新拉取 `/api/config` 刷新令牌并**重试一次**；仍失败才提示
- 报错文案人话化："操作失败，已尝试自动恢复令牌。请刷新页面重试；若仍失败，在终端重新执行 /dashboard"
- 安全边界说明写入代码注释：该令牌是 CSRF 盾，不是访问凭证（服务只绑 127.0.0.1）

### 2.3 验收标准

- [ ] 重启 pi / 重新执行 /dashboard 后，旧标签页上传、编辑字典等写操作直接成功
- [ ] 令牌文件权限 0600；删除令牌文件后重启自动重建
- [ ] 人为制造令牌失配（改文件内容），前端一次写失败后自动恢复成功
- [ ] vitest：令牌持久化/复用/重建 + 前端重试逻辑（可对 api.fetch 包装器抽函数单测）

## 5. A-3：表卡片（P2，知识工程核心）

### 5.1 为什么做（设计依据）

当前 system prompt 对表只有"N 行 M 列"，模型选错表、不知道表存在、不知道表数据不全（边界）是高频故障。字段字典是列级语义、指标定义是度量语义，表卡片补上表级"目的/边界/时机"语义，三者拼完整。卡片同时是导航层（A-4）的原子内容。

### 5.2 数据模型

```typescript
interface TableCard {
  tableName: string;
  summary: string;            // 一句话：这是什么表
  suitableFor: string[];      // 适合什么（分析场景/问题类型）
  boundaries: string[];       // 边界：不含什么、时间范围、已知坑
  whenToUse: string[];        // 什么时候需要找它（触发词/场景）
  tags: string[];             // 分类标签（导航分组用，v0.10 不做层级目录）
  status: "ai-drafted" | "user-confirmed";
  fingerprint: string;        // dataset fingerprint，表结构变化时标记 stale
  stale: boolean;
  updatedAt: string;
}
```

- 存储：`.pi-data-agent/table-cards.json`，复用 AtomicStore（revision 乐观锁）
- 起草：load_data 成功后 fire-and-forget（不阻塞、失败静默）；LLM 输入 = schema + 5 行样本 + 该表近期查询记忆（query memory 按 fingerprint 召回）；无 LLM 时生成 schema 推导的骨架卡（summary 留空待填）
- 表结构变化（fingerprint 不匹配）→ 标记 stale，提示重新起草

### 5.3 Dashboard 落点（语义 Tab）

- 表级区块：卡片字段编辑器（summary/suitableFor/boundaries/whenToUse/tags）+ "AI 起草"按钮 + 状态徽章（AI 起草/已确认/已过期）+ "确认"动作
- 数据 Tab 的表预览头部显示卡片 summary 一行（无卡片显示占位提示）

### 5.4 API

```
GET  /api/table-cards              # 全部卡片（导航用）
GET  /api/table-cards/:table
PUT  /api/table-cards/:table       # 用户编辑（expectedRevision 乐观锁）
POST /api/table-cards/:table/draft # AI 起草（无 LLM 返回 503，同字典推断约定）
```

### 5.5 验收标准

- [ ] 上传新表后（配置了 LLM）语义 Tab 出现 AI 起草卡片；无 LLM 出现骨架卡
- [ ] 编辑并确认后 status 变为 user-confirmed，重启仍在
- [ ] 表重新加载且结构变化 → 卡片标记 stale
- [ ] vitest：存储读写/乐观锁/stale 标记/骨架生成；起草 API 的 503 分支

## 6. A-4：导航注入 + get_table_card（渐进式披露 L0+L1）

### 6.1 架构决策（本版本只做 L0+L1）

```
L0 常驻导航层（before_agent_start，预算 ≤400 token）
   每表一行：表名 · 标签 · 一句话 summary（无卡片则退化为 N 行 M 列）
   + 固定指标名（A-6）+ 高频/固定 SQL 指针（A-5）
   超预算时：先只列分类标签，提示模型用工具下钻
L1 按需取用层（扩展工具）
   get_table_card(table_name)：完整卡片 + 该表字典摘要（已确认字段含义优先）
L2 即时注入层（query_data 执行前经 tool_call 钩子附加卡片/指标）→ v0.11
```

- 选型说明：L1 用扩展自有工具而非 MCP——零新增基础设施、能力等价；MCP 仅在将来需要让 pi 之外的 Agent 共享知识库时再评估。Skills 不用于承载数据资产（动态、频繁编辑），技能目录继续只放操作规程。

### 6.2 实现要点

- `before_agent_start`：现 "Current Data Context" 块替换为导航层；查询记忆/口径注入保留但各自加预算上限（超限按相关性截断）
- system prompt 规则追加一句："写 SQL 前如不确定表用途/边界，先调 get_table_card"

**get_table_card 聚合装配规则**（自身不存知识，只做三源读取与拼装）：

```
1. 表卡片 ← table-cards.json（主键即表名）
   无卡片时用 schema 生成骨架并注明"待补充"
2. 相关指标 ← metrics.json，过滤条件：metric.datasets 包含该表（定义指标时勾选的数据集即为关联键）
   命中 ≤5 条，每条取 名称+计算规则；0 条省略该节
3. 字段字典 ← 合并后的字典视图（session > project > global）
   该表全部列按可信度排序：已修正 > 已确认 > AI推测(标"未确认") > 不确定(标"不可靠")
   只取前 15~20 个字段
```

- 三块知识各住原库，本工具零自有存储；与 Dashboard 同一数据源，编辑即时生效
- 返回体 300~500 token 属正常（模型主动索取，不设硬限）；固定模板分节：【表卡片】【相关指标口径】【字段业务含义】
- 兜底：无卡片→骨架；无相关指标→省略该节；字典为空→提示可在 Dashboard 跑 AI 推断

### 6.3 验收标准

- [ ] 10+ 张表时 system prompt 导航段 ≤ 预算（测试用字符数近似断言）
- [ ] 模型可调用 get_table_card 拿到完整卡片；表不存在时返回可用错误
- [ ] 无卡片表在导航中退化为行列数展示，不报错
- [ ] get_table_card 返回包含三节内容且排序/数量上限符合装配规则；Dashboard 编辑字段含义后立即反映在返回中
- [ ] vitest：导航渲染（含预算截断）、工具返回结构、三源聚合拼装

## 9. 明确推迟到 v0.11

| 项 | 原因 |
|----|------|
| 视觉整体翻新（统一卡片/留白/字号层级） | 等信息架构稳定后一次做，避免返工 |
| L2 即时注入（query_data 自动附卡片/指标） | 依赖 A-3/A-4 落地后的实际使用反馈 |
| MCP 服务暴露知识库 | 仅当需要 pi 之外 Agent 共享时再做 |
| 字典 AI 推断交互重做 | 等用户补充"不好用"的具体表现 |
| 表分类的自动聚类/层级目录 | v0.10 先用 tags，表多了再演进 |

### 9.1 L2 即时注入——设计预埋（v0.11 直接照此实施）

**职责划分**：L1 工具由**模型**决定何时调用（prompt 规则引导）；L2 由**钩子**自己读知识库注入上下文，钩子不代替模型调工具。

**触发条件（四条同时满足）**：
1. 目标识别：从 SQL 的 FROM/JOIN 解析出已登记表名，或 user_intent 命中已定义指标名
2. 知识存在：该表有卡片（含 stale）、命中指标定义、或 SQL 触及字典中 uncertain 状态字段
3. 尚未消费：本会话"已交付清单"中不存在（见下）
4. 预算内：单次附注 ≤200 token，每轮最多覆盖 2 张表

**"已交付清单"语义**：session 级内存 Set，键为 `tableCard:<表名>@<fingerprint>` 与 `metric:<id>`。
- 写入时机：L2 附注发生时；get_table_card 成功返回时（同一张表不再重复附注）
- 重置时机：新会话自然为空；表 fingerprint 变化（重新加载且结构变了）；会话压缩（compaction）完成后整体清空（早期注入可能已被压缩掉，需重新交付一次）

**注入形态两级**：
- 提示类（默认，不拦截）：query_data 结果前附边界/口径提醒。实现优先在 query_data 工具内部（执行后拼接），备选 tool_result 事件增强
- 冲突类（例外，拦截重写）：仅当高置信度违反已确认指标口径——user_intent 点名某指标 + SQL 聚合该指标的度量列 + 缺失定义中明确写有的过滤条件 → 复用 active-questioning 拦截机制，附定义原文让模型改写后重新提交。初期判定保守，宁可漏拦不可误拦

**pi 能力依据**（已核实 @earendil-works/pi-coding-agent 类型定义）：`tool_call` 钩子可 block，且 `event.input` 可原地改写（官方注释明确支持）；存在 `tool_result` 事件可触达结果内容。

**指标获取路径**：
- v0.10 阶段：不需要独立指标工具。get_table_card 返回时由服务端按 `metrics.datasets` 关联拼入相关指标的完整定义；且指标数量少时全量以"名称+一行定义"常驻 L0
- 指标超过约 20 条后：L0 退化为仅列指标名，新增独立工具 `get_metric(name)` / `search_metrics(keyword)`（独立小工具，不让 get_table_card 兼职）

**预算总览**：L0 常驻 ≤400 token（地图）；L1 工具返回 300~500 token 属正常（模型主动索取，不设硬限）；L2 自动附注单次 ≤200 token、每轮 ≤2 张表。

### 9.2 表分类演进路线预埋

原则：分类只为导航预算与检索效率服务，导航没超预算就不升级结构。

- **阶段 1（≤20 张表，v0.10）**：扁平 tags，导航每表一行；AI 起草时建议标签，语义 Tab 可改
- **阶段 2（30+ 张表 / 导航逼近预算）**：
  - 导航改两级：分类行 → 该类代表表
  - 新增 `search_tables(keyword)` 工具作检索兜底
  - 新表自动归类双来源：① 来源血缘免费送——load_data 进来标"原始层"、transform_data（CTAS）产出标"加工层"；② 受控词表——AI 只能从用户维护的标签集合里选，用户确认生效
  - 仍不做文件夹树：标签分组 + 搜索足够
- **阶段 3（100+ 张表 / 多项目）**：知识库独立为本地目录服务（届时评估 MCP），导航层只剩分类清单，检索成为主要访问路径

## 11. 风险与降级

| 风险 | 概率 | 影响 | 降级方案 |
|------|------|------|----------|
| 令牌持久化被误读为安全弱化 | 低 | 低 | 注释 + README 说明威胁模型（本机 CSRF 盾） |
| 表多导致导航超预算 | 中 | 中 | 分类优先截断 + 工具下钻（设计内行为） |
| 无 LLM 时卡片起草不可用 | 中 | 低 | schema 骨架卡兜底，用户可手填 |
| IA 重构遗漏旧 Tab 功能入口 | 中 | 中 | 按 0.1 清单逐项核对 + 人工验收 |
| metrics 旧数据迁移冲突 | 低 | 中 | 迁移失败保留原文件并告警，不阻塞启动 |
| pinned 注入撑爆 L0 | 低 | 低 | pinned 注入条数上限（如 10 条） |
