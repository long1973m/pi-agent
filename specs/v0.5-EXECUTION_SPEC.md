# Pi Data Agent v0.5 执行 Spec｜网页端可视化进阶(SQL卡片+字典面板+多Session浏览)

## 背景

v0.4 已完成:消息流 + 图表内联的 HTML 报告,自动生成、自动打开浏览器,零常驻服务。v0.4 Spec 里 Deferred 的三项,构成 v0.5 的主线:

1. SQL 卡片(展示实际执行的 SQL 语句,带语法高亮)
2. 数据字典面板(展示字段确认状态)
3. 更完整的多 Session 浏览 / 切换能力

v0.5 继续沿用 v0.4 定下的架构原则:**不引入常驻服务、不做协议桥接、单份 HTML 离线自包含**。多 Session 浏览也在这个约束下实现——不是做实时服务器切换,而是生成一份静态的报告索引页。

## v0.5 定位

网页端可视化 · 第二步:让报告"更专业"——看得到 SQL、看得到字典状态、能在历史报告间跳转

## 任务拆解(按执行顺序)

### Task 1｜SQL 提取与轻量语法高亮

- **文件**:`src/report/sql-highlight.ts`(新建)
- **做什么**:
    - 从工具调用记录里提取 SQL 相关字段(`query_data` 的 sql 参数、`connect_database` 实际执行的语句)
    - 写一个轻量 tokenizer(正则匹配关键字 / 字符串 / 数字 / 注释),输出带 `<span class="sql-kw">SELECT</span>` 这类标记的 HTML
    - **不要**引入 highlight.js 等外部库或 CDN 依赖——v0.4 定的"报告完全离线自包含"约束在 v0.5 继续生效
- **验收**:覆盖以下 SQL 结构的人工验证，确保着色正确、无误判：
    - 关键字：`SELECT`、`INSERT`、`CREATE`、`WITH`、`JOIN`、`FROM`、`WHERE`、`GROUP BY`、`ORDER BY`
    - 字符串：单引号、双引号、包含转义符的字符串
    - 数字：整数、浮点数、科学计数法
    - 注释：`--` 行注释、`/* */` 块注释
    - 复杂结构：子查询（`SELECT * FROM (SELECT ...)`）、CTE（`WITH t AS (...)`）、多表 JOIN
    - 至少 10 条真实场景 SQL（从 v0.1~v0.4 的测试用例和实际分析记录中提取）

### Task 2｜SQL 卡片渲染

- **文件**:`src/report/html-template.ts`(改造)
- **做什么**:
    - 消息流里,如果某个工具调用节点命中 SQL 类工具,不再用 v0.4 的简化摘要卡片,改为渲染 Task 1 输出的高亮 SQL 块
    - 卡片默认折叠展示前 3 行,点击展开查看完整语句(用 `<details>`,不需要额外 JS)
- **验收**:一个包含多轮 SQL 查询的 session 生成报告后,人工检查每条 SQL 都能展开查看、格式不错乱。

### Task 3｜数据字典状态面板

- **文件**:`src/report/dictionary-panel.ts`(新建)
- **做什么**:
    - 读取本次 session 涉及数据集的字典状态：**通过 `persistence.loadDictionary()` 从持久化层读取，不从内存缓存读**。确保跨 session 生成报告时状态正确
    - 渲染为表格:字段名 | 类型 | 状态 | 说明
    - 状态用颜色标签区分:`user-confirmed` 绿色、`ai-guessed` 黄色、`user-corrected` 蓝色、`uncertain` 红色
    - 面板放在报告顶部,默认折叠(`<details>`),避免喧宾夺主
    - **时效性保障**:字典确认操作完成后立即调用 `persistence.saveDictionary()` 落盘,确保报告生成时读到的字典状态是最新的,而非旧缓存
- **验收**:一个用过 `confirm_dictionary` 工具的 session,生成报告后面板里的状态与实际确认结果一致。

### Task 4｜报告索引页(多 Session 浏览)

- **文件**:`src/report/build-index.ts`(新建)
- **做什么**:
    - 每次生成新的 session 报告后,扫描 `reports/` 目录下所有 `session-*.html` 文件
    - 从文件名解析时间戳,从报告内的 `<meta>` 标签读取任务摘要(需要 Task 5 配合在生成报告时写入 meta)
    - 生成 / 覆盖 `reports/index.html`:按时间倒序列出所有历史报告,标题+时间+摘要,点击跳转到对应报告
    - **兜底处理**:解析旧报告(v0.4 生成,可能无 `<meta>` 标签)时,fallback 到文件名时间戳 + "无摘要",不因缺少 meta 而导致索引页构建失败。解析失败时 log warning（如 `console.warn('[build-index] Failed to parse meta from ...')`），方便排查，不阻塞构建
    - **容错**:索引页中链接的报告文件可能已被用户手动删除,链接失效时显示"报告文件已移除"而非整页崩溃
    - **不要做**:不做搜索、不做分页,先解决"能跳转"这一个问题
- **验收**:连续生成 3 次报告后,`index.html` 里能看到 3 条记录,顺序正确,点击都能正常跳转。手动删除一个报告文件后,索引页对应条目显示"报告文件已移除"。

### Task 5｜generate_session_report 集成

- **文件**:`src/tools/generate-session-report.ts`(改造,注意不是 `generate-report.ts`)
- **做什么**:
    - **保持 v0.4 的向后兼容承诺**:`generate_report`（数据报告）保持不变,不修改其 schema 或逻辑。v0.5 的增强全部集成到 `generate_session_report`（会话报告）中
    - `generate_session_report` 流程里插入 Task 1+2(SQL 卡片)、Task 3(字典面板)、Task 4(索引页刷新)
    - 报告 HTML 头部写入 `<meta name="summary" content="...">` 供 Task 4 索引页解析,摘要内容用当次任务的第一句用户提问即可,不需要额外生成逻辑
    - 自动打开浏览器时默认打开**本次报告**,同时在报告顶部加一个"查看全部历史报告"的链接指向 `./index.html`（相对路径）。移走报告文件后链接自然失效不报错
- **验收**:端到端跑一次分析任务,确认最终打开的是本次报告,且报告顶部链接能正确跳到索引页。v0.4 的 `generate_report` 工具行为无变化。

### Task 6｜Should Have(时间允许再做,不阻塞验收)

- 字典面板增加前端过滤按钮(纯 `<script>` 内嵌,按状态筛选行,不依赖外部库)
- SQL 卡片增加"复制"按钮(`navigator.clipboard`,注意 `file://` 协议下部分浏览器会限制该 API,需做降级——失败时提示手动选中复制,不报错阻断)
- 索引页里每条记录增加"涉及数据集"标签

**验收检查项（即使 Task 6 做了也要验证）**:
- [ ] `file://` 协议下点击复制按钮有降级提示，不报错
- [ ] 浏览器地址栏显示 `file://...` 时复制功能可用或提示手动复制

### Task 7｜测试与回归

- **文件**:`acceptance-v5.sh`(新建,参考 `acceptance-v4.sh` 结构)
- **测试场景(至少 3 个真实分析任务)**:
    1. 单数据源多轮 SQL 查询 → 生成报告 → 断言每条 SQL 都被正确高亮且可展开
    2. 首次连接新数据集,触发字典确认流程 → 生成报告 → 断言字典面板状态与实际确认结果一致
    3. 连续跑 3 次独立分析任务 → 断言 `index.html` 正确列出 3 条记录且可跳转
- **回归**:跑一次 v0.1~v0.4 现有回归测试,确认新增代码没有破坏已有工具(尤其是 v0.4 的报告生成与自动打开浏览器流程)。

## Deferred to v0.6+

- 真正的多会话实时对比(并排展示两次会话的结果差异)

## 验收标准

- Task 7 的 3 个场景 + 回归测试全部通过
- SQL 卡片、字典面板在无网络环境下依然正确显示(继续满足离线自包含要求)
- `index.html` 索引页能正确反映所有历史报告,且不影响单份报告本身"发给别人也能独立打开"的特性(索引页是可选的附加页面,不是必需依赖)
- 新增内容不影响 v0.4 已验收的消息流 + 图表内联能力
- v0.4 的 `generate_report`（数据报告）行为无变化（向后兼容验证）

## 风险与注意事项

- 手写 SQL tokenizer 覆盖不了所有边界情况(比如复杂嵌套子查询、少见方言语法),验收时用真实场景里出现过的 SQL 覆盖即可,不需要做成通用 SQL parser
- `navigator.clipboard` 在 `file://` 协议下可能受限,复制按钮必须有可用的降级提示
- 索引页依赖历史报告文件仍然存在于 `reports/` 目录,如果用户手动删除了某些报告文件,索引页需要能容错(链接失效不报错,而不是整页崩溃)
- Task 5 集成到 `generate_session-report.ts`,**不**改造 `generate-report.ts`,保持 v0.4 "两个报告工具独立并存"的承诺

## 备注

Pi Data Dashboard 三层架构策划文档(Bridge/Server/Client)继续暂缓。v0.5 用静态索引页的方式覆盖了"多 Session 浏览"里最核心的诉求,如果后续发现这个模式确实有明显瓶颈(比如报告数量太多导致索引页臃肿、需要实时看正在跑的 session),再回头评估是否真的需要引入服务器。
