# Pi Data Agent v0.7 执行 Spec｜正式分析报告 + AI 数据字典预填

<aside>
📝

版本定位：v0.7 = 分析产物质量升级。把"分析过程记录"和"正式分析报告"拆成两类产物，并让数据字典从"用户从零填写"升级为"AI 先生成候选含义，用户确认或修正"。

</aside>

> **核心目标**：让 Pi Data Agent 不仅能完成分析，还能输出一篇证据可靠、结构清晰、适合业务阅读的正式报告；同时降低数据字典建设成本，为后续语义查询资产奠定字段语义基础。
> 

> **版本边界**：v0.7 不实现业务口径与 SQL 的正式资产化，不改变 Agent 的 SQL 查询规划主链路；相关能力在数据结构上预留关联字段，正式实现延后至 v0.8。
>

- PII 脱敏是否支持字段样本值；
- Dashboard 报告列表与字典页面的现有 API。

如果真实实现与本文档不同，优先复用现有模块，通过 adapter 适配，不重写成熟链路。

## 2. 核心设计原则

1. **过程报告与正式报告并存**：前者服务追溯，后者服务阅读和决策。
2. **证据先于写作**：先构建结构化 Evidence Package，再调用模型写报告。
3. **模型不负责重新计算数字**：量化结果来自查询结果或确定性计算。
4. **结论必须可追溯**：正式报告中的关键数字、图表和结论关联证据 ID。
5. **事实与解释分开**：直接证据、推断性解释、待验证假设使用不同标签。
6. **AI 字典只是候选**：AI 推断永远不会自动变成 `user-confirmed`。
7. **不覆盖用户知识**：默认只填充空字段，不覆盖 `user-confirmed` 和 `user-corrected`。
8. **低置信度宁可不猜**：证据不足时输出 `uncertain`，不能编一个听起来合理的含义。
9. **批量而非逐字段调用**：控制延迟、成本和上下文一致性。
10. **兼容现有 Dashboard**：在现有页面增量扩展，不复制新的管理页面。

## 3. 双报告模型

### 3.1 Session Report

定位：分析底稿、过程回放和审计档案。

保留内容：

- 完整用户与 Agent 消息；
- 工具调用；
- SQL；
- 查询结果摘要；
- 图表；
- 数据字典状态；
- Session 时间线。

现有生成逻辑继续保留，不因 v0.7 改造成正式报告。

### 3.2 Analysis Report

定位：面向业务阅读、决策和交付的正式分析成稿。

默认结构：

```
报告标题

执行摘要
- 3～5 条核心结论
- 关键影响

1. 分析背景与问题
2. 数据范围与业务口径
3. 关键发现
   3.1 结论 + 数据证据 + 图表 + 业务解释
   3.2 ...
4. 原因分析
5. 行动建议
6. 风险、限制与待验证事项
附录：证据索引、核心 SQL、字段口径、Session Report 链接
```

### 3.3 两类报告的关联

```
Session
├── session-report-<id>.html
└── analysis-report-<id>.html
        └── sourceSessionReportId
```

- 正式报告必须记录来源 Session；
- 正式报告可跳转到过程报告；
- 过程报告中显示"基于本 Session 生成的正式报告"；
- 一个 Session 允许生成多个正式报告版本；
- 正式报告不得覆盖旧版本。

## 4. 正式报告生成流程

```
用户显式请求生成报告
    ↓
识别报告类型与分析范围
    ↓
检查 Session 是否存在足够分析结果
    ↓
构建 Evidence Package
    ↓
运行证据完整性检查
    ↓
模型生成 Report Draft JSON
    ↓
运行事实与引用校验
    ↓
确定性 HTML Renderer 渲染
    ↓
写入报告文件与 manifest
    ↓
Dashboard 展示 + 打开浏览器
```

### 4.1 触发规则

支持：

```
/report
/report executive
/report detailed
```

自然语言触发示例：

- "生成一份正式分析报告"；
- "把这次分析整理成管理层能看的报告"；
- "输出详细分析报告"。

规则：

- Session Report 可继续按现有策略自动保存；
- Analysis Report 只在用户明确要求时生成；
- 不因普通"总结一下"自动生成 HTML 正式报告；
- 如果分析尚未完成或证据不足，先明确缺失内容，不生成伪完整报告。

### 4.2 `/report` 命令

推荐使用 Pi Extension 自定义命令，不注册成 Agent Tool：

```tsx
pi.registerCommand("report", {
  description: "基于当前分析生成正式报告",
  getArgumentCompletions(prefix) {
    return ["executive", "detailed"]
      .filter(v => v.startsWith(prefix))
      .map(v => ({ value: v, label: v }));
  },
  async handler(args, ctx) {
    // 解析 mode → 获取当前 Session → 生成报告 → 通知结果
  },
});
```

自然语言请求仍由 Agent 调用现有报告生成能力；斜杠命令是确定性的用户控制入口。

实现方式沿用 v0.6 `/dashboard` 命令的实际注册模式（在 `index.ts` 中通过 `extension.registerCommand` 注册），handler 内部直接调用 `generateAnalysisReport()` 函数，不经过 Agent Tool 调度链路。

## 5. Evidence Package

### 5.1 目标

Evidence Package 是正式报告的唯一事实输入，避免模型直接从冗长聊天记录中自由总结。

### 5.2 推荐结构

```tsx
interface EvidencePackage {
  version: 1;
  sessionId: string;
  question: string;
  reportMode: "executive" | "detailed";
  scope: {
    datasets: string[];
    dateRange?: { start: string; end: string };
    filters: Array<{ field: string; operator: string; value: unknown }>;
  };
  metrics: MetricSnapshot[];
  findings: FindingEvidence[];
  charts: ChartEvidence[];
  queries: QueryEvidence[];
  dictionary: DictionarySnapshot[];
  limitations: Limitation[];
  generatedAt: string;
}
```

### 5.3 FindingEvidence

```tsx
interface FindingEvidence {
  id: string;
  statement: string;
  evidenceType: "direct" | "derived" | "hypothesis";
  resultRefs: string[];
  chartRefs: string[];
  queryRefs: string[];
  metricRefs: string[];
  confidence: "high" | "medium" | "low";
  caveats: string[];
}
```

含义：

- `direct`：查询结果直接支持；
- `derived`：由多个结果经过确定性计算得到；
- `hypothesis`：可能解释，尚未验证。

### 5.4 QueryEvidence

至少保存：

- query ID；
- 自然语言问题；
- SQL；
- 成功/失败状态；
- 数据集；
- 执行时间；
- 结果字段；
- 行数；
- 用于报告的摘要结果；
- 是否被 Finding 引用。

失败、过时或未执行 SQL 不得作为正式报告的直接量化证据。

### 5.5 证据构建规则

1. 优先读取结构化工具结果，不从 Agent 自然语言回答中反推数字；
2. 图表必须关联其原始查询或结果；
3. 每个量化 Finding 至少有一个 resultRef 或 chartRef；
4. 百分比必须保留分子、分母或计算来源；
5. 时间比较必须保留两个时间窗口；
6. 无法确认来源的结论移入 hypothesis 或 limitations；
7. Evidence Package 保存为 JSON，便于回归测试和后续重渲染。

推荐路径：

```
.pi-data-agent/reports/evidence/<analysis-report-id>.json
```

### 5.6 证据来源优先级

构建 Evidence Package 时，按以下优先级读取数据，不得为构建证据重新执行 SQL 查询：

```
1. Session transcript 中已有工具调用结果（query_data / visualize / show_image 的返回值）
2. data-dictionary.json 当前 revision 快照
3. query-memory.json 中的 SQL 和结果摘要
4. metrics.json 中的口径定义
5. DuckDB describe_data 实时 schema（仅当 transcript 中无记录时补充）
```

不得重新执行查询——如果 Session 结束后数据被修改，报告应反映分析时的数据状态，而非当前状态。

## 6. Report Draft 结构

模型输出结构化 JSON，不直接输出最终 HTML。

```tsx
interface AnalysisReportDraft {
  title: string;
  executiveSummary: Array<{
    text: string;
    findingRefs: string[];
  }>;
  background: string;
  scope: string;
  sections: Array<{
    heading: string;
    conclusion: string;
    evidenceRefs: string[];
    chartRefs: string[];
    interpretation?: string;
    interpretationType?: "supported" | "hypothesis";
  }>;
  recommendations: Array<{
    action: string;
    priority: "high" | "medium" | "low";
    rationale: string;
    findingRefs: string[];
  }>;
  limitations: string[];
}
```

### 6.1 模型约束

System/Prompt 中明确：

- 只能引用 Evidence Package 中的信息；
- 不得创造新数字；
- 不得把 hypothesis 写成确定性原因；
- 不得删除会改变结论的重要限制；
- 没有行动建议依据时允许不写建议；
- 每个核心结论必须返回 findingRefs；
- 输出必须通过 schema 校验。

### 6.2 失败与重试

- JSON 解析失败：使用同一 Evidence Package 重试一次；
- schema 不合法：返回具体字段错误，定向修复一次；
- 引用了不存在的 evidence ID：拒绝渲染并重试；
- 两次仍失败：保留 Evidence Package，向用户报告失败，不生成不可靠报告。

## 7. 报告质量门槛

### 7.1 自动质量检查

| 检查项 | 规则 |
| --- | --- |
| 引用完整性 | 所有 evidenceRefs、chartRefs 必须真实存在 |
| 数字来源 | 正文中的关键数字必须能在 Evidence Package 中找到 |
| 结论覆盖 | 每条执行摘要至少关联一个 Finding |
| 推测标识 | hypothesis 必须使用"可能、待验证"等表达 |
| 口径一致性 | 报告使用生成时的 Metric Snapshot，不读取未来版本覆盖历史 |
| 时间范围 | 涉及趋势、同比、环比必须声明时间窗口 |
| 图表上下文 | 图表包含标题、指标、单位、时间范围和来源 |
| 限制保留 | Evidence Package 中高优先级 limitation 不得被模型删除 |

### 7.2 证据覆盖率

```
coverage = 有有效证据引用的核心结论数 / 核心结论总数
```

- `coverage = 100%`：可发布；
- `< 100%`：不得标记为正式报告；
- hypothesis 不计入量化核心结论，但必须明确标识。

### 7.3 正式报告视觉要求

- 开头直接展示执行摘要，不展示聊天记录；
- 每个关键发现使用"结论 → 证据 → 图表 → 解释"的顺序；
- SQL 默认放入折叠附录；
- 字典与口径默认放入附录；
- 支持离线打开；
- 与 Dashboard 现有主题保持一致；
- 打印和导出 PDF 时不出现导航按钮、调试信息和交互控件。

## 10. AI 数据字典预填

### 10.1 目标

当新数据集首次加载或字典业务含义为空时，AI 生成候选含义。用户从"从零填写"改为"确认或修正"。

### 10.2 推断输入

每个字段允许使用：

- 表名；
- 字段名；
- 数据类型；
- 数据库原始注释；
- 少量脱敏样本；
- 空值率；
- 唯一值数或近似值；
- 最小值、最大值；
- 同表其他字段；
- 主键、外键或 join 关系；
- 历史 SQL 中的聚合、过滤、连接方式；
- 已确认业务口径；
- 已确认的同表字段含义。

不得发送：

- 未脱敏 PII；
- 大量原始数据行；
- 与推断无关的其他表数据；
- 本机路径、密钥或连接凭据。

### 10.3 推断输出

```tsx
interface DictionarySuggestion {
  table: string;
  column: string;
  suggestedDescription: string;
  suggestedAliases: string[];
  status: "ai-guessed" | "uncertain";
  confidence: number;
  confidenceLevel: "high" | "medium" | "low";
  evidence: string[];
  uncertainties: string[];
  modelVersion: string;
  generatedAt: string;
  sourceSchemaRevision: number;
}
```

示例：

```json
{
  "table": "orders",
  "column": "amount",
  "suggestedDescription": "订单金额，可能为用户实际支付金额",
  "suggestedAliases": ["订单金额", "支付金额"],
  "status": "ai-guessed",
  "confidence": 0.76,
  "confidenceLevel": "medium",
  "evidence": [
    "字段类型为 DECIMAL",
    "历史查询经常使用 SUM(amount)",
    "大部分样本值为正数"
  ],
  "uncertainties": [
    "无法确认是否含税",
    "无法确认是否已扣除退款"
  ]
}
```

### 10.4 置信度规则

不要求模型自报分数直接作为最终置信度。服务端结合证据确定等级：

```
高：存在数据库注释、稳定值模式或多个一致证据
中：字段名、类型、SQL 用法基本一致，但关键口径未确认
低：主要依赖字段名猜测，样本或上下文不足
```

推荐状态映射：

- high / medium → `ai-guessed`；
- low → `uncertain`；
- 任何置信度都不能自动成为 `user-confirmed`。

### 10.5 生成时机

自动触发：

```
首次加载新数据集
    ↓
Schema 扫描完成
    ↓
筛选 description 为空的字段
    ↓
按表批量生成候选含义
    ↓
schema 校验 + 原子保存
```

手动触发：

- `[为缺失字段生成含义]`；
- `[重新推断选中字段]`；
- `[查看推断依据]`。

保护规则：

- 自动模式只处理空字段；
- 不覆盖 `user-confirmed`；
- 不覆盖 `user-corrected`；
- `uncertain` 只有用户主动选择时才重新推断；
- Schema revision 变化时标记建议可能过时，不直接清除用户内容；
- 同一 Schema revision 的相同字段使用缓存，不重复调用模型。

## 11. AI 字典推断流程

```
收集表级 Schema 与统计信息
    ↓
PII 脱敏与字段筛选
    ↓
按表组装 Dictionary Inference Context
    ↓
一次模型调用生成整表候选
    ↓
JSON Schema 校验
    ↓
字段存在性与类型校验
    ↓
置信度规则修正
    ↓
原子写入 data-dictionary.json
    ↓
Dashboard 提示用户审核
```

### 11.1 为什么按表批量推断

- 同表字段存在上下文关系；
- 减少模型调用次数；
- 避免同义字段解释不一致；
- 能利用主键、时间字段、金额字段之间的组合判断。

默认每次最多处理 100 个字段；超过时按字段组分批，并在最终写入前检查重复与冲突。

### 11.2 失败降级

- 模型不可用：保留空字段，Dashboard 显示"AI 建议暂不可用"；
- JSON 解析失败：重试一次；
- 部分字段失败：成功字段可以保存，失败字段标记 inference_error；
- 统计超时：仅使用 Schema 和脱敏样本，并降低置信度；
- 写入冲突：返回 409，重新加载 revision 后只合并仍为空的字段。

## 12. 字典数据结构扩展

在现有字段结构上增量扩展，不另建第二份字典真源：

```json
{
  "name": "amount",
  "type": "DECIMAL",
  "description": "订单金额，可能为用户实际支付金额",
  "status": "ai-guessed",
  "aliases": ["订单金额", "支付金额"],
  "suggestion": {
    "confidence": 0.76,
    "confidenceLevel": "medium",
    "evidence": ["字段类型为 DECIMAL"],
    "uncertainties": ["是否含税尚未确认"],
    "modelVersion": "model-id",
    "generatedAt": "2026-07-19T11:00:00+08:00",
    "sourceSchemaRevision": 8
  },
  "review": null
}
```

用户确认后：

```json
{
  "status": "user-confirmed",
  "review": {
    "action": "confirmed",
    "reviewedAt": "2026-07-19T11:10:00+08:00"
  }
}
```

用户修改后：

```json
{
  "description": "订单应付金额，含税，退款前",
  "status": "user-corrected",
  "review": {
    "action": "corrected",
    "originalSuggestion": "订单金额，可能为用户实际支付金额",
    "reviewedAt": "2026-07-19T11:12:00+08:00"
  }
}
```

保留原始建议只用于评测和回溯，不作为 Agent 当前业务含义注入上下文。

### 12.1 sourceSchemaRevision 实现方式

现有 `DataDictionaryEntry` 使用 `schemaFingerprint`（MD5 hash 字符串）标识 Schema 版本。`sourceSchemaRevision` 复用该字段：

- `sourceSchemaRevision` 类型为 `string`（与 `schemaFingerprint` 一致），而非递增整数；
- 检测 Schema 变化：比较 `currentSchemaFingerprint !== suggestion.sourceSchemaRevision`，若不一致则标记建议"可能过时"；
- 不引入独立的递增计数器，避免维护两套版本标识。

## 14. Agent 上下文使用规则

### 14.1 字典状态权重

```
user-corrected > user-confirmed > ai-guessed > uncertain
```

- `user-corrected`、`user-confirmed`：可作为可靠业务语义；
- `ai-guessed`：可用于辅助理解，但生成 SQL 或结论时需标记未确认；
- `uncertain`：不得作为确定性业务口径；必要时主动向用户提问。

### 14.2 正式报告使用规则

- 报告"数据与口径"章节标明哪些字段仍为 AI 推测；
- 关键指标依赖未确认字段时，加入 limitation；
- 不因字典有预填内容就跳过重要口径确认；
- 用户在生成报告前修正字典时，Evidence Package 使用最新 revision 快照。

## 19. 人工验收

1. 完成一次包含查询和图表的真实分析。
2. 打开 Session Report，确认仍是完整过程记录。
3. 输入 `/report detailed`，生成正式分析报告。
4. 检查报告是否直接给出核心结论，而不是复制聊天记录。
5. 随机抽查所有量化结论，确认能定位查询结果或图表。
6. 检查原因推测是否明确标注为待验证。
7. 在 Dashboard 中切换"正式报告 / 分析过程记录"。
8. 从正式报告跳到来源 Session Report，再从 Session 返回正式报告。
9. 加载一个新数据集，确认空字典获得 AI 建议。
10. 查看某字段的置信度、证据与不确定点。
11. 确认一个建议，状态变为 user-confirmed。
12. 修改一个建议，状态变为 user-corrected。
13. 重新打开 Dashboard，确认修改持久化且 AI 原始建议可回溯。
14. 使用包含未确认字段的指标生成报告，确认限制章节有提示。
15. 运行 v0.1～v0.6 全量回归测试。

## 20. 发布判定

### 可发布条件

- Session Report 与 Analysis Report 明确分离；
- 正式报告不复制完整对话，结构符合业务阅读逻辑；
- 正式报告关键数字和结论 100% 通过证据引用校验；
- hypothesis 与已验证事实明确区分；
- 报告可回到来源 Session；
- 新数据集空字段可获得 AI 候选含义；
- AI 建议包含置信度、依据和不确定点；
- AI 不覆盖用户确认或修正内容；
- 字典模型失败不会破坏原文件；
- PII、revision、原子写入和审计继续生效；
- v0.1～v0.6 回归无退化。

### 不可发布条件

- 正式报告仍以聊天时间线为主要结构；
- 报告出现 Evidence Package 中不存在的数字；
- 推测性原因被写成确定事实；
- 无证据时仍生成看似完整的正式报告；
- AI 字典建议自动变成 user-confirmed；
- 自动推断覆盖用户修正；
- 未脱敏样本发送给模型；
- 模型解析失败导致 data-dictionary.json 损坏；
- v0.6 Dashboard 或原 Session Report 退化。
