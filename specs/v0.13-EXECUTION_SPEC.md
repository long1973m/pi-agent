# Pi Data Agent v0.13 执行 Spec｜外部数据库连接阶段 2：远程表物化到本地

<aside>
🔧

版本定位：v0.13 = 数据库连接阶段 2（调研口径 4–6 人天，主要成本在大表熔断策略与测试替身）。范围来自 `research/database-connection-research.md` §「阶段 2：物化到本地再分析」；前置依赖 v0.12 已交付（commit a8a6ed2…08378d5：MySQL 只读 ATTACH + RemoteDbDialect 基座 + M-8 连接视图）。PostgreSQL（阶段 3）留给 v0.14。

</aside>

> **核心目标**：① 新工具 `materialize_remote_table`——把已 ATTACH 的远程表复制为本地 main 库的一等公民数据集（`list_datasets` / 字典 / 表卡片 / 可视化全链路可用）；② 大表熔断 + tmp→rename 原子替换，失败不留脏表；③ 物化后自动进字典，与 CSV 上传路径对齐。
>
> **安全红线（贯穿全部任务）**：物化只允许工具实现层发起（模型侧对远程表的大批量 CTAS 仍走既有 confirm 门）；本地写操作沿用 S-1 fail-closed 确认门（headless 无豁免不执行，除非 autoConfirmWrite）；超阈值必须 block 而非 confirm——大数据量对生产 MySQL 的全表扫描压力不该靠"顺手确认"放行。

### 0.2 关键设计决策：测试替身用 sqlite ATTACH

调研指出的主要成本是"大表熔断策略与测试替身"——本机无 MySQL（v0.12 §12 已确认继续挂起）。**解法：物化工具的目标源不限于 mysql 方言，接受任何非 main/memory 的已 ATTACH 数据库别名**（sqlite 文件 attach 即可充当测试替身）。

理由：
- 物化的本质是 `CREATE TABLE main.x AS SELECT * FROM <alias>.<tbl>`，对 DuckDB 而言 sqlite/mysql/postgres attached 别名行为一致；
- 收紧到"仅 mysql 方言"没有安全增益（sqlite 文件本来就是本地白名单路径），反而堵死测试路径；
- 白名单、凭据、只读等安全边界在**连接层**（v0.12 已收口），物化层不需要重复设防。

### 0.3 开发前必须核验

- [ ] sqlite ATTACH 替身下 `CREATE TABLE main.tmp AS SELECT * FROM sqlite_alias.tbl` 全链路可跑（预期成立，跑通一次）
- [ ] DuckDB 事务内 `DROP TABLE IF EXISTS + ALTER TABLE ... RENAME TO` 的原子性（单连接 `engine.exec("BEGIN")...COMMIT` 即可，确认无需 SAVEPOINT）
- [ ] `ALTER TABLE ... RENAME TO` 在 DuckDB v1.5.x 的语法与权限行为
- [ ] 远端 `SELECT COUNT(*)` 下推确认：物化前的规模探测不应把全表数据拉到本地（用 EXPLAIN 或耗时特征确认 pushdown 生效）

## 3. RM-2：`materialize_remote_table` 工具（P0）

### 3.1 参数

| 参数 | 说明 |
|------|------|
| `alias` | 必填。已 ATTACH 的数据库别名（非 main/memory；mysql/sqlite/postgres 均可，见 §0.2） |
| `table` | 必填。远程表名 |
| `target_table` | 可选。本地表名，默认 `{alias}_{table}` 归一化；**与 main 现有表重名时确认门文案必须声明"将替换"** |
| `row_limit` | 可选。只物化前 N 行；大于 `dbMaxMaterializeRows` 时 block |

参数 schema 无敏感字段（凭据在连接层，物化参数只涉及表名）。

### 3.2 执行流（六步）

1. **校验**：alias 已 ATTACH（查 `duckdb_databases()`）且非 main/memory；`alias.table` 存在（复用 enumerateAttachedTables 模式查 information_schema）
2. **规模探测**：`SELECT COUNT(*) FROM alias.table`（依赖 v0.12 已确认的 pushdown，远端计数）
3. **熔断**：`count > dbMaxMaterializeRows` 且无 `row_limit` → **block**（不是 confirm）。文案给出三条出路：设 `row_limit` 小于阈值 / 调大 `PI_DATA_AGENT_DB_MAX_MATERIALIZE_ROWS` / 在远端先过滤（WHERE 走 query_data + 物化子集）
4. **确认门**：`resolveConfirmGate`（S-1 语义——本地写操作，headless 无 autoConfirmWrite 即 block）。确认文案必须包含：预估行数、目标表名、是否替换现有表
5. **tmp → rename 原子替换**：
   ```sql
   CREATE TABLE main._materialize_tmp AS SELECT * FROM alias.table LIMIT row_limit;  -- 失败即整体失败
   BEGIN; DROP TABLE IF EXISTS main.target; ALTER TABLE main._materialize_tmp RENAME TO target; COMMIT;
   ```
6. **返回摘要**：目标表名、行数、列数、耗时、endpoint（无凭据）；若源表含 `DECIMAL(p>38)` 列（落地为 DOUBLE）必须在摘要中显式提示精度坑（调研 §4.4）

### 3.3 明确不做

| 项 | 说明 |
|----|------|
| `columns?` 列裁剪参数 | 调研方案里有，但模型完全可以用 query_data 先建视图/子集；工具保持窄接口 |
| 增量同步 / 定时刷新 | 真实需求出现再议（数据一致性语义复杂：主键对账 vs 全量替换） |
| 物化后自动 DETACH 远程 | 连接生命周期属阶段 3（v0.14 连接管理） |
| 跨库 JOIN 物化 | 模型用 query_data 的 CTAS（confirm 门内）即可完成，不进工具 |

## 4. RM-3：失败回滚 + 体积护栏（P1，stretch）

- 任一步失败：`DROP TABLE IF EXISTS main._materialize_tmp`，**绝不触碰已有 target**；错误文本过 `redactCredentials` 后返回
- `.duckdb` 文件体积护栏：物化前后 `statSync(dbPath)` 体积记录进返回摘要；超 `dbMaxDbSizeMb`（如引入）熔断回滚——行数熔断已覆盖主要风险，此项等真实需求再做，先只做体积记录

### 验收标准

- [ ] CREATE 失败后：tmp 无残留、target 原样、可立即重试
- [ ] rename 阶段失败（模拟：注入非法 target）后同上
- [ ] 返回摘要含 .duckdb 体积变化

## 5. RM-4：物化后自动进字典（P0）

### 5.1 方案要点

直接复用 load_data 的 hooks 模式（`src/tools/load-data.ts:268-387`）：

- `dataDictionary.ensureDictionary(target, engine)` 静默生成字典（失败不影响物化结果，返回 `dictionaryGenerated` 标志）
- 表卡片骨架兜底由既有 `get_table_card` 逻辑承担，不额外起草卡
- 返回文本提示"已生成了数据字典，可用 confirm_dictionary 校正"

### 5.2 验收标准

- [ ] 物化成功后 `list_datasets` 可见目标表、字典状态为 ai-guessed
- [ ] 字典生成失败不影响物化成功返回

## 10. 风险与注意事项

| 风险 | 说明 | 对策 |
|------|------|------|
| 大结果集压垮生产 MySQL | `mysql_sql_buffer_result=true` 会把压力推给服务端（调研 §4.3） | 行数熔断默认 500_000；block 而非 confirm；文案引导远端过滤 |
| 物化中途失败留脏数据 | 全量单语句无部分回滚 | tmp→rename 事务模式；失败 DROP tmp；T-1 #10 专项 |
| target 重名静默覆盖 | 用户不知情丢表 | 确认门文案显式声明"将替换"；audit.log 记录 |
| DECIMAL(p>38) 精度丢失 | 落地 DOUBLE（调研 §4.4） | 返回摘要显式提示；README 记录 |
| sqlite 替身与真机行为差异 | 替身测试不覆盖 mysql 特有类型坑 | 类型坑提示基于调研文档；真机验收补验（§9） |
| `ALTER TABLE RENAME` 语法差异 | DuckDB 版本间行为变化 | §0.3 开发前核验项 |
